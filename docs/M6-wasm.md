# M6 — Ядро на C++ → WebAssembly (SIMD)

Заготовка для главы диплома. Код: `wasm/core.cpp`, `wasm/build.sh`, `src/wasm-sim.js`, `bench/bench.mjs`.

## 1. Что перенесено
Шаг симуляции целиком (`step`): предсказание, ограничения расстояния/площади (M1–M2), коротационный FEM (M3), напряжения, столкновения кусков со spatial grid (M5), границы окна. Топологические операции (разрез ножом, расщепление вершин при разрыве, подсчёт кусков) остались в JS: они редкие и работают с теми же массивами.

## 2. Архитектура
- Сборка без Emscripten: `clang --target=wasm32 -ffreestanding -nostdlib` + `lld`, без libc (только `__builtin_sqrt` и т. п.). Результат — модуль ~9 КБ (scalar) и ~14 КБ (SIMD). Установка: `sudo apt install clang lld`, затем `wasm/build.sh`. Готовые `.wasm` лежат в `src/wasm/`.
- Все массивы состояния лежат в линейной памяти WASM; поля `sim.x`, `sim.tris`, … в JS — TypedArray-представления на неё. Копирования между JS и WASM нет, рендер и нож читают те же данные.
- Параметры передаются через два массива (`ctx_f64`, `ctx_i32`): числа и смещения массивов. Порядок индексов зеркально повторён в `wasm-sim.js`.
- `memory.grow` делает представления недействительными, поэтому память выделяется один раз при `buildSlab` (с запасом под расщеплённые вершины), и представления создаются заново только при пересборке.

## 3. Проверка корректности
Скалярное ядро выполняет те же операции в том же порядке, что JS (в JS `Math.hypot`, `atan2`, `cos/sin` в горячих путях заменены на `sqrt` и алгебру). 10 сценариев (падение, консоль, M1, M2, разрыв рёбер, эрозия, растяжение с трещинами, нож + падение + столкновения) дают **побитово одинаковые** позиции (max Δx = 0, одинаковые число кусков, контактов, трещин).

## 4. SIMD
- Элементы раскрашены жадно (на сетке получается 8 цветов): элементы одного цвета не делят вершин, значит 4 из них можно решать одновременно; цвета идут последовательно (Гаусс–Зейдель по цветам). Раскраска пересчитывается при каждом изменении топологии.
- Ядро FEM на `f32x4`: разности рёбер считаются в f64, тяжёлая математика (деформация, полярное разложение, sqrt, деления, градиенты ограничений) — в f32x4, поправки накладываются на позиции в f64. В WASM SIMD нет векторных gather/scatter, они скалярные.
- Результат **не** побитовый (другой порядок обновлений и f32), поэтому проверяются инварианты: нет NaN, 0 вывернутых элементов, суммарная площадь совпадает с JS (67255 vs 67254), энергия того же порядка. Хаотичные сценарии (удар об пол, разрушение) расходятся — это ожидаемо.
- Ловушка: `v128_t` в clang — вектор `int64x2`, операторы `* + -` над ним работают как целочисленные; нужен собственный тип `float __attribute__((vector_size(16)))`.
- Поддержка проверяется `WebAssembly.validate`; без SIMD интерфейс использует скалярный WASM.

## 6. Ограничения
- Скалярное ядро выигрывает у JS всего ×1.2–1.8: JIT V8 уже хорошо оптимизирует эти циклы; основной выигрыш даёт SIMD.
- Столкновения (M5) пока скалярные; следующий шаг — векторизация и мультипоточность (WASM threads).

## 7. Детализация (больше частиц)
Ползунок «Детализация» ×k делает шаг сетки в k раз мельче (плита той же величины, частиц ≈ k²: ×4 → 3.5 тыс., ×8 → 13.6 тыс., ×12 → 30 тыс.), число подшагов растёт от 10 до 20. Замеры в Chromium (контейнер, без столкновений): ×4 — SIMD 3.9 мс против JS 11 мс; ×8 — 15 мс против 40 мс.

Ограничение: на очень мелкой сетке сильный удар (падение с высоты) выворачивает часть элементов — за подшаг вершина проходит больше размера элемента (то же происходит в JS, это свойство метода, а не WASM). Помогает больше подшагов, меньшая гравитация или падение с меньшей высоты; полноценное решение — непрерывное обнаружение столкновений / адаптивные подшаги (задел на M7).

## 8. Оптимизация (M6.4)
Профиль на 30 тыс. элементов (SIMD): ≈1.1 мс на подшаг (≈37 нс на элемент) + ≈2 мс за кадр на пересчёт напряжений. Вывод: время уходит на вычисления (два полярных разложения, sqrt/деления), а не на память. Проверено на практике: перенос данных элементов в порядок раскраски (SoA, чтения подряд), чтение позиций один раз на группу из 4 элементов, одна суммарная запись поправок — ускорения не дали (в пределах шума), поэтому оставлены как более чистый вариант ядра.

Что реально помогло:
- **Пропуск `cutStep`** (JS, O(T) за кадр): ядро отдаёт максимальное напряжение элементов, и если оно ниже прочности, поиск вершин для разреза не запускается (осреднённое по вершине напряжение не может превысить максимум по элементам). Экономия ≈9 мс/кадр на 30 тыс. элементов при включённых трещинах.
- **Ползунок «Подшаги»** (4…30): время кадра почти линейно зависит от числа подшагов — это прямой обмен скорости на устойчивость.
- **«Авто-подшаги»**: число подшагов зависит от максимальной скорости вершины в прошлом кадре (вершина не должна пройти за подшаг больше ≈0.15 шага сетки), минимум 8. На ×8: 18 → 12 мс/кадр. Цена — при сильном ударе чуть больше вывернутых элементов, поэтому по умолчанию выключено.

Дальше (M7): параллельный FEM в нескольких потоках (раскраска уже даёт независимые группы), непрерывное определение столкновений, пересчёт напряжений реже, чем раз в кадр.

## 9. Потоки (M7.1)
Сборка `core.simd.mt.wasm`: те же ядра, но память общая (`SharedArrayBuffer`), рабочие потоки — Web Workers (`src/wasm-worker.js`), которые подключаются к той же памяти и входят в `worker_loop`. В `step()` главный поток раздаёт параллельные задачи (FEM по цвету, пересчёт напряжений): записывает параметры, увеличивает счётчик поколений, потоки по очереди берут куски работы через атомарный счётчик (динамическое распределение — медленные ядра big.LITTLE просто делают меньше кусков), главный поток тоже работает и ждёт счётчик завершения (в браузере он не может блокироваться, только крутиться в цикле). Рабочие после короткого простоя засыпают (`atomic.wait`), чтобы не греть процессор между кадрами.

Корректность: элементы одного цвета не делят вершин, поэтому записи не пересекаются; результат **побитово не зависит от числа потоков** (проверено: контрольная сумма позиций при 1 и 2 потоках совпала).

Требования: страница должна быть кросс-доменно изолирована (заголовки `Cross-Origin-Opener-Policy: same-origin` и `Cross-Origin-Embedder-Policy: require-corp`) — они прописаны в `vite.config.js` для dev и preview. На обычном статическом хостинге их нужно включить (например, файл `_headers` на Netlify). Без изоляции пункт «WASM SIMD + потоки» недоступен, интерфейс остаётся на обычном SIMD.

Замер в контейнере (2 ядра), 30 тыс. элементов, 20 подшагов: 24.1 мс (1 поток) → 14–17 мс (2 потока). Масштабирование на 4+ ядрах нужно мерить на целевом телефоне.
